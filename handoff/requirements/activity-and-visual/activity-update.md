## 1. 产品方向与首发默认决定

### 1.1 品牌与定位

用户可见产品名称统一为 **同野·游**。应用标题、PWA 名称、导航、帮助、分享文案、空状态和 README 更新一致。不得擅自设计新英文品牌名或重做同野品牌体系。

定位：**围绕一场活动，安排自己的行程，也安排与朋友同行的时间。**

“凑空”可以作为功能用语继续出现，例如“小队里的共同空闲”，但不再作为整站产品名。旧数据库键、协议 kind、URL 兼容标识不能因为改品牌而全局替换。

### 1.2 这次采用的默认产品决定

- 公开活动由管理员创建、编辑并发布；普通用户先选活动再使用。
- 未加入小队也可以浏览公开活动、收藏摊位、整理个人计划和规划路线。组队是增强，不是所有操作的前置条件。
- 小队默认不公开，凭邀请加入，不进入全站活动搜索或成员排行榜。
- 继续提供不依赖短信、邮箱注册的使用方式。个人身份和恢复凭据沿用或扩展当前安全实现，不临时引入完整账号中心。
- 公共活动资料和私人小队资料严格区分。队长不能改全站公共活动，也不能读取或修改队员的私人备注。
- 地图是活动资料的一部分，不要求接入收费地图服务。先把实际地图、可信标点和通道做对，再考虑自动定位。
- 首发服务小规模真实使用，不宣传支持万人实时协作。性能与额度要实测，不用无限扩容的承诺替代指标。
- 用户仍可发起约饭、自习等日常安排：从“发起日常活动”建立未公开的通用活动及小队，不强迫先申请管理员发布。

### 1.3 如何参考 2dg.ai

参考地址：`https://2dg.ai`。只参考其公开可见的“先选活动，再进入活动内使用”的信息组织原则，不复制页面布局、配色、组件、文案、Logo、地图素材或数据库。

用户明确要求不照搬。“更好”落实为本项目可验收的体验，而不是对对方产品作未经验证的贬低：

1. 收藏、场次、个人安排、地图、路线、小队时间能连贯操作，不是互相孤立的工具页。
2. 不组队也能使用，收到邀请能直接进入对应活动与小队，不绕回首页重新选择。
3. 分钟级计划、明确的同步状态和资料版本，避免看起来好看但现场信息不可靠。
4. 有弱网准备和离线快照，地图失败时列表与日程仍可用。
5. 管理员不用改源码，就能发布活动、上传地图、标点和维护通道。
6. 隐私默认合理，收藏不被强制公开，定位不自动上传。

## 2. 信息结构：活动是入口，小队是活动内的关系

### 2.1 首页和活动选择

首页主要显示管理员已发布的活动，支持名称搜索、活动类型筛选和日期状态；只有少量活动时不要堆复杂筛选器。显示必要的名称、日期、地点、类型与资料更新时间。

- 活动列表与“我最近参加”分开，后者不得泄露私人小队信息。
- 无数据、加载、错误和已结束活动分别有正常状态。
- 点击活动后进入活动空间，始终能清楚看到当前活动和日期，并能切换活动。
- 不根据最近一次访问强制跳走，尤其不能覆盖邀请链接携带的目标。
- 日常活动入口保留，但不要与管理员的“发布公共活动”混为一个按钮。

### 2.2 活动内的移动端结构

漫展类型推荐保持四个主要入口：

- **逛展**：活动概况、地图、摊位/设施搜索、详情、收藏与场次入口。
- **计划**：自己的收藏清单、当天安排、路线；用页面内切换组织，不再新增一排底部导航。
- **同行**：我的小队、创建/加入小队、成员状态、共同空闲、集合提议。
- **我的**：个人偏好、身份恢复、导出、离线准备、帮助；不展示无意义的数据仪表盘。

通用类型的第一个入口叫“活动”，不显示空的摊位和地图管理内容。图标、顺序与视觉保持统一，业务标签按类型变化。

桌面端可以增加并列信息，但不能另造一套业务流程。现有合适的 Sheet、行列表、时间轴和设计 token 继续使用；不要把手机页面改成满屏后台卡片和常驻编辑器。

### 2.3 深链接和上下文

至少有可直达的活动、摊位/地点、场次、个人计划和小队页面。URL 中的 `eventId` 与资源真实归属必须一致。

- 打开小队邀请直接定位活动及小队，必要时仅完成身份确认。
- 从日程点地点进入正确地图并高亮该地点，返回后保留日期、滚动和未提交草稿。
- 从摊位详情加入场次后，能到个人计划继续编辑。
- 切换活动不能把同编号摊位的收藏串到另一个活动。
- 刷新、浏览器返回、微信内打开和 PWA 冷启动必须正常。
- 保留旧 URL 和旧分享格式的兼容入口；重定向不得把权限令牌写到查询串或日志。

## 3. 三种角色：权限明确，不让用户理解内部结构

### 3.1 管理员

管理公共活动及版本、活动类型、活动说明与来源、地图资产、摊位与设施、活动场次、通道数据、发布/下架和必要的滥用处理。可以预览普通用户视角。

管理员本人想逛展时可以建立自己的个人计划或小队，但管理会话不能直接充当所有人的个人编辑凭据。

### 3.2 队长

在活动下建队、邀请、管理本队成员和回复状态、设置本队候选时间范围、关闭/归档小队、提出集合时间地点和同行路线。

队长不能覆盖公共地图和公共场次。需要自定义时使用本队私有配置，明确其非公共资料属性。队长不能冒充队员确认安排或打开其私密备注。

### 3.3 队员

维护自己的资料、收藏、计划和可参与时间，加入或离开小队，查看允许共享的成员状态与共同空闲，自主确认集合提议。

没有加入小队的人仍是普通使用者，只是尚无队伍关系，不新增一套“第四角色”的管理系统。浏览公开页面不要求登录或注册。

### 3.4 权限不可仅靠隐藏按钮

所有 API 必须验证角色、资源归属和数据范围。测试直接请求：队长改公共活动、成员改他人计划、跨队读取、跨活动操作、已撤销凭据继续写入，都应失败。

## 4. 活动类型与管理员创建流程

### 4.1 类型字段

建立稳定的 `eventType` 或等效字段，不通过标题中是否包含“漫展”判断功能。

首发必须真正实现：

- `generic`：通用活动。
- `comic_convention`：漫展。

结构允许未来扩展市集、音乐节、校园活动、旅行，但没有实际差异化流程的类型不要展示为已经完成的专门产品，也不建复杂插件市场。

已有无类型活动安全归为通用类型；已明确为 REDLAND 的资料可由管理员确认后迁为漫展类型，不能仅靠模糊名称自动迁移。

### 4.2 创建和编辑

管理员先选类型，再填活动基础资料。字段至少包括名称、简介、完整日期、活动时区、每日开放区间、地点、来源说明；漫展类型展开地图、摊位/设施、场次和通道管理。

提供“网页表单编辑”和“JSON 导入”两条真实可用路径。导入是方便批量录入，不是要求管理员只能写 JSON。

- 状态：草稿、已发布、已归档；取消活动需有独立明确标记，不等于删除。
- 发布前校验名称、日期、开放时间和所有已启用模块的数据完整性。
- 漫展没有地图也可以发布，但地图入口显示资料未提供，不出现假地图。
- 地图未标注通道可以看图和地点，但不能假称可导航。
- “已发布”与“来源已核实”分开。管理员发布不自动使其成为官方资料。
- 切换类型不能悄悄删除已有漫展扩展数据。先展示影响；有成员使用时采用非破坏性变更与复核。
- 只有管理员能将活动列入公共入口，队长导入的私有活动不能通过修改 JSON 字段自动公开。

## 5. 个人计划与小队数据的关系

### 5.1 活动内个人状态

建立或复用稳定的“此人在此活动内的个人记录”，集中关联：收藏、想去/去过状态、个人安排、路线草稿、个人设置与加入的小队。

这不是要求建设全站账号。优先沿用当前免注册能力凭据，用适配层连接现有成员模型。不得为增加收藏而推翻已完成的鉴权。

目标行为：

- 用户在地图收藏后，计划页立即能看到，不要求先加入小队。
- 后续加入小队，不需要重建自己的所有安排。
- 同一活动参加两个小队时，个人计划有稳定来源；提交时明确同步哪些小队的回复。若各队配置版本不同，应提示需要分别复核，不静默覆盖。
- 小队只能获得用户已确认共享的忙闲投影，不因内部关联而拿到收藏、路线或私人备注。
- 在不具备安全自动合并条件时，展示一次清楚的迁移/关联确认；不能按昵称把两个身份合并。

### 5.2 持久化和恢复

收藏、去过状态与路线顺序必须刷新后仍在；网络可用时通过当前在线存储保存，不仅存在组件内存。离线写入本地待同步，并明确状态。

首次建立匿名个人记录应在请求前持久化恢复所需的高熵身份材料，解决“服务器已经创建、响应丢失”的重试问题。恢复入口要可保存，不能靠重新输入相同名字认领。

普通个人数据导出默认不带管理员或队长凭据。恢复凭据单独处理，日志、截图、公开文档不泄露。

### 5.3 三件事绝对不能混为一谈

- **收藏**：想去，不占用时间，不代表已预约。
- **加入安排**：用户明确选了日期与时间，才影响其日程；仍不代表完成官方报名。
- **加入路线**：希望按一定顺序经过该地点；只有再次确认排入时间安排，才改动日程。

“去过”是用户手动标记，不推断为已完成官方签到或预约。取消收藏不自动删除已有预约；删除路线也不删除收藏或场次。

## 6. 漫展地点、摊位和场次

### 6.1 地点模型

建立稳定的地点/POI 实体，类型可包括摊位、舞台、入口、出口、服务台、卫生间、餐饮、医疗点、休息区、集合点。

必要字段：稳定 ID、名称、分类、可选展位编号、可选标签/IP、描述、地图定位、来源说明和数据更新时间。名称不是主键，两个活动都可有 A-09。

场次与地点关联使用 ID，不能靠比较地点文本。一个地点可对应多个活动/场次；没有场次的摊位也可以收藏和加入路线。某些场次没有已确认地点，应允许未知，而不是强行写成 `(0,0)`。

### 6.2 用户侧操作

搜索支持名称、展位编号和标签；大小写、前后空格、常见编号连字符差异不应造成明显漏搜，但不得错误合并不同地点。

地图和列表共用选中状态与收藏状态。地点详情包含必要资料、相关场次、收藏、加入路线、查看地图；不要强行显示全部空字段。

个人收藏至少支持按区域/地图筛选、仅看未去过、手动去过标记。收藏完整绑定活动与地点 ID，改显示名称后仍保留；地点被移除时提示失效，不转移到同名新地点。

没有真实来源时，不显示实时排队人数、库存、预计抽奖成功率或“当前人少”等虚构信息。

## 7. 地图：先可靠看图和标点，再做路线

### 7.1 上传与资产存储

管理员能从网页上传 PNG/JPEG/WebP 地图，预览、命名、替换并选择适用地图/区域/楼层。不是只把图片选到浏览器里，也不是要求每次改 GitHub 源码才能上传。

首发可先完成单地图，但数据结构必须允许多地图；多区域展示可实现，多楼层跨图路线不作为首发阻断。

上传要求：

- 校验权限、字节上限、真实文件类型、尺寸、像素总量；拒绝伪装 HTML、脚本、SVG 和超限文件。首发不接 PDF/动图自动转换。
- 默认产品上限建议：每张源图 12 MiB、24 百万像素、每活动 5 张；生成适合移动端的显示版本并保持文字可读。具体上限须对实际存储和运行时实测，前后端、文档一致。
- 不无声过度压缩。源图与衍生显示图分别有元数据；原图是否长期保留、是否供下载需有清楚策略。
- 去除不需要的照片 EXIF 定位等元数据；不在公开 JSON 带上传者私人信息。
- 对象存储放图片，业务数据库放资产标识、哈希、尺寸、版本和引用。不把大图 base64 塞进每个小队 JSON 或 D1。
- 成功上传后再完成数据库引用，状态区分上传中、校验中、可用、失败；失败不能留下“已发布但打不开”的地图。
- 草稿/私有资料不得因使用公开图床而被无认证访问。公共可见资产与私有资产的策略分别实现、分别说明。
- 资产 URL 不得携带长期管理员密钥。不能用浏览器拿到的 Blob Object URL 当成永久地址。
- 公共地图必须有来源/授权记录。可让用户手动上传有权使用的官方公开图，不从竞品复制素材或去除其署名。

### 7.2 标点坐标约定

以实际地图图像的左上角为原点，内部统一使用归一化坐标 `x,y ∈ [0,1]`，x 向右、y 向下，关联 `mapId` 和地图版本。

地图画面、点位、通道线、路线必须共用同一套变换。保持图片宽高比；容器留白不计入地图坐标。使用 Leaflet CRS.Simple、Canvas/SVG 或现有合适技术均可，但要封装轴顺序，不能把图像坐标误当经纬度。

管理员能在图上点选地点、拖动微调、编辑坐标、删除并撤销误操作。缩放平移时不能误放点。提供列表与缺定位筛选，方便批量补点。

换图规则：

- 仅等比例重采样且构图不变，可经预览确认复用点位。
- 裁剪、旋转、改布局或换底图，必须进入“需重新校对”状态，不能认为归一化坐标会自动保证位置正确。
- 原版本及其引用保留到迁移/回滚完成；不要替换同一路径后假定旧缓存已更新。

### 7.3 地图使用体验

支持移动端平移、双指缩放、回到全图、地点高亮、过滤收藏、列表查看。密集标点需适当聚合或按缩放控制标签，不能一屏重叠文字。

地点详情使用底部 Sheet 或原有统一组件，不让用户在地图上打开多层遮罩后无法返回。列表是地图不能加载、无障碍和低性能设备的可用替代，不是占位说明。

地图不因深色模式被反色处理而破坏图例。必要时只调整周围 UI 和标点，不改底图含义。

## 8. 路线：区分参观顺序与可走路径

### 8.1 首发必须有的路线能力

- 将收藏地点或已有场次地点加入当天路线。
- 选择起点，优先支持“从某入口/某摊位出发”和手动声明位置，不依赖定位权限。
- 调整站点顺序，手机有上移/下移替代，不只支持鼠标拖拽。
- 按日程顺序查看已有固定场次的地点，固定预约不得被优化器调换时间。
- 有经过人工确认的通道数据时，按通道生成可走路径；缺数据时保留站点清单并明确不能生成对应路段。
- 路线支持保存、刷新恢复、标记经过、从剩余站点继续查看。路线重算不修改原始收藏和确认的预约。

不能把几个标点直接连线就称为导航。没有通道时可以显示编号地点，但不画看似可走、实际穿过摊位或障碍物的实线路径。

### 8.2 通道标注的最小可用后台

管理员能在地图中建立通道节点并连线，编辑折线几何，设置双向/单向、可用/关闭，以及可选的已知距离或估计通行时间。

- 通道是人工依据真实资料确认的可通行路径，不是 AI 从图片猜出的线。
- 地点与路网入口需要明确连接；不能以欧氏最近点自动穿墙连接。
- 交叉线是否连通以共享节点为准，图上相交不自动成为路口。
- 通道可先覆盖入口和这次实际需要的摊位，不要求完整测绘全场。
- 未确认边不参与“可走路径”计算。局部覆盖允许发布，但必须显示覆盖范围/缺路段。
- 支持关闭边、关闭日期和方向；对跨图连接、楼梯、电梯，未实现时明确不支持，不能画直线跨楼层。
- 无障碍属性为未知时不能当成已确认无障碍路径。首发没有实现无障碍路径筛选，就不显示相关承诺。

### 8.3 算法与计量

首发用可测试的图最短路算法（例如 Dijkstra）计算已确定站点顺序的各段路径。可以在浏览器 Web Worker 中完成，避免让每次拖动都请求后端；数据与逻辑仍应有自动化测试。

- 权重必须使用同一种单位。已知通行秒数优先用于时间路径；缺少时间但有同一图内几何权重时，只提供相对顺路结果。
- 地图图像像素不是米。没有有效比例尺、实测距离或人工通行时间，就不显示精确“多少米/几分钟”。
- 部分路段缺时间，整段 ETA 应标为无法完整估计，不能把未知路段计为 0。
- 有距离换算时间时注明步行速度是假设；排队时长由用户输入或明确默认假设，不伪装成实时数据。
- 不连通时返回明确缺失路段，不偷偷改为直线导航。
- 日期、临时关闭和方向必须进入计算条件。不能使用过期通道后仍标为当前有效。
- 多站点“减少折返”是后续增强；实现时明确为启发式建议，不声称全局最优，不能为了多逛几个摊位而错过固定预约。

### 8.4 与时间安排的连接

时间精度继续保留到分钟，路径内部可以使用秒，不向整点或整刻舍入已有安排。

首发先做“到下一场是否有足够时间”的建议，不让路线计算自动改写共同空闲算法。

为避免重复计算移动时间，统一约定：

- 原有个人缓冲视为两场之间的基本移动预留。
- 直接从上一固定场次到下一固定场次的检查，所需移动预留取 `max(路线通行时间, 上一场后缓冲 + 下一场前缓冲)`，不要再把同一交通需求叠加两次。
- 插入额外游逛时，另加用户确认的停留和排队时间，均计入总可用间隔。
- 使用已经扣过缓冲的共同空闲窗口安排一次同行时，不再次扣同一缓冲；共同游逛的实际行程必须装进该窗口。
- 来源位置或时间未知时显示“无法判断”，不推断为赶得上。
- “时间上都空闲”不自动等于“所有人能赶到同一集合点”。集合建议需要成员明确回应。

路线时间是估计，不保证现场排队、临时封路和安全通行情况。必要提醒简洁可见，详细限制写入帮助。

## 9. 实时定位：可选增强，不阻塞 REDLAND

首发必须有手动起点，自动定位放在 P1。不能为了定位耽误地图、收藏、日程、小队、上传和上线。

确实实现定位时：

1. 用户点击“定位我”才请求权限；使用 HTTPS 与浏览器 Geolocation API，处理拒绝、超时、不支持和定位不可用。
2. 浏览器返回的是地理坐标，不是这张活动地图上的像素。只有地图完成可信地理配准后才投影当前位置。
3. 明确 WGS84 与底图坐标体系；不能把不同坐标系的数据直接相减或直接叠加。
4. 示意图、艺术化地图或比例扭曲的地图不一定适合配准；无法建立可信变换时，禁用图内自动定位并保留手动起点。
5. 若采用仿射配准，控制点要足够且非共线，并有独立检查点或额外控制点评估误差。不能用恰好三个点拟合后“残差为零”声称定位准确。
6. 显示定位精度和数据新鲜度；精度差、超出配准范围或数据过期时不做自动吸附与路线更新，提示手动选择。
7. 不宣称室内精准定位、知道所在楼层或持续后台导航。普通网页定位不能被包装成摊位级保证。
8. 定位默认只在本机参与显示与计算，不发送到服务器、不存轨迹、不把实时位置共享给队友。共享实时位置是独立未来需求，不随本功能悄悄加入。
9. 停止定位、离开页面或切换不适用地图时注销监听，隐藏页面采取节电策略；反复拒绝权限后不循环弹窗。
10. 定位失效不影响其他功能，关闭该功能不破坏数据结构和路由。

## 10. 同行：保留原来的核心，并与活动连接

继续完整实现管理员、队长、队员范围内的建队、邀请、个人时间提交、成员选择和共同空闲。

### 10.1 原时间规则不得回退

- 存储、JSON、手动输入和算法精确到 1 分钟。
- 快捷选择默认 15 分钟，可切 5/10/15/30 分钟；手动可填 `13:07–13:52`。
- 日内区间左闭右开；24:00 仅作结束边界；跨午夜按明确日期拆分，缓冲正确溢出到相邻日期。
- 日期有年份，小队按活动时区展示，不由设备时区暗中平移。
- 多段开放时间、多段可参与时间、个人独立缓冲都保留。
- 未填写、草稿、已确认、需复核分开；空数据不自动等于全天有空。
- 共同空闲只依据选中成员的已确认有效数据。选中但未确认的人不能被静默忽略。
- 改显示步长不能改变任何已存时间或交集结果。

继续通过原精确回归样例：活动 09:00–12:00，A 可来 09:00–12:00、忙 10:07–10:22、缓冲 5 分钟，B 可来 09:15–11:50、忙 09:40–09:55、缓冲 0；未过滤交集为 09:15–09:40、09:55–10:02、10:27–11:50。

### 10.2 集合提议

首发可以提供一个轻量且完整的集合提议：队长从共同空闲中选择时间，选择已标注地点，发布给本队；队员明确接受/拒绝/尚未回复。

提议不是队员已确认的安排，不自动把所有人的日程改为忙碌。修改时间或地点后使原回应失效并重新询问。确实无法在首发完成该流程时，保留共享地点链接作为明确降级，不展示假的“全队已确认”。

只公开成员自愿分享的共同目标或路线。不默认通过“共同收藏”展示谁私下收藏了什么；统计也需明确参与范围。

## 11. 版本与更新：资料变化不能把用户安排弄乱

至少区分以下版本/含义，命名沿用当前实现也可以：

- 活动时间配置版本：日期、开放区间、场次起止变化，影响已确认安排。
- 空间版本：地图、标点、路网、关闭信息变化，影响路线。
- 个人计划版本：个人安排、收藏或路线等对应资源的并发控制。
- 普通内容修订：纯标题、说明等不改变时间或位置语义的修改。

要求：

1. 改地图描述不让全队重填时间；改场次起止必须要求受影响用户复核。
2. 换图、移点、关路后，既有路线标明过期并要求重算；不得继续用旧路线配新底图。
3. 小队引用公共活动的版本策略要明确。既有快照不被悄悄覆盖；公共页面新版本与本队确认版本不同时给出复核入口。
4. 遇到活动取消、地点封闭、地图撤回等重要状态，在使用旧快照时也提醒其已失效，不能把“固定旧版本”当作信息永不失效。
5. 收藏通过稳定地点 ID 保留，失效地点显示失效，不自动替换为同名地点。
6. 备份中包含对应地图/图数据版本引用，恢复后可识别缺失资产。
7. 数据库写入使用 expectedRevision/CAS 和操作幂等。多人编辑失败时保留草稿，不能后写覆盖。
8. 数据与媒体不能假装共用一个数据库事务。使用分阶段上传、校验、发布引用和可清理孤立资产，防止部分失败后损坏线上版本。

## 12. JSON 标准与资产导入：升级但兼容

### 12.1 不能因改名破坏旧协议

先读当前已经实现的活动包与 Schema。原标准曾为 `kind: "coukong.event"`、`schemaVersion: 1`。

- 原 kind 可保留为技术兼容名；品牌和协议标识不是同一回事。
- 新增类型、地图、POI、路网属于结构升级；若现有最高版本仍为 1，则定义版本 2。若 dots 已实施更高版本，使用下一个合适版本并写迁移表。
- 继续接受已发布的旧版本，迁移为 generic/空地图，不丢原时间、活动和场次。
- 原 JSON 严格校验不能因为扩展就关闭，不允许“任意字段都接受”。

### 12.2 建议的扩展结构

在原 event 里新增类型及明确的扩展块，通用字段不重复一套。逻辑关系如下；字段命名若已有同义实现，应统一而不是平行新增：

- Event：原基础字段＋`eventType`＋`extensions.convention`。
- Map：`id`、`title`、`assetKey`、`width`、`height`、`revision`、固定图像坐标约定，地理配准另作可选版本化数据。
- POI：`id`、`name`、`kind`、`boothCode?`、`tags?`、`position?`、`routeNodeId?`、来源。
- Position：`mapId`、`x`、`y`，明确绑定地图版本。
- Session：原日期起止＋可选 `poiId`；已有 location 文本保留为说明，不代替引用校验。
- RoutingGraph：版本、地图 ID、nodes、edges；每条边有稳定 ID、from、to、方向、几何折线、可用状态，可选距离/通行秒数；不混用计量单位。
- AssetManifest：逻辑 assetKey、类型、尺寸、大小与哈希。它只描述文件，不赋予读取其他活动资产的权限。

示意（不是可以直接覆盖原 event 的完整活动包）：

```json
{
  "eventType": "comic_convention",
  "extensions": {
    "convention": {
      "maps": [
        {
          "id": "map-demo",
          "title": "示例场地图",
          "assetKey": "demo-map.webp",
          "width": 2000,
          "height": 1000,
          "revision": 1,
          "coordinateSpace": "normalized-image-top-left"
        }
      ],
      "pois": [
        {
          "id": "poi-demo",
          "name": "示例摊位",
          "kind": "booth",
          "boothCode": "A-09",
          "position": {
            "mapId": "map-demo",
            "mapRevision": 1,
            "x": 0.25,
            "y": 0.6
          },
          "routeNodeId": "node-demo"
        }
      ],
      "routingGraphs": [
        {
          "id": "graph-demo",
          "mapId": "map-demo",
          "mapRevision": 1,
          "revision": 1,
          "nodes": [
            {"id": "node-entry", "x": 0.1, "y": 0.6},
            {"id": "node-demo", "x": 0.25, "y": 0.6}
          ],
          "edges": [
            {
              "id": "edge-demo",
              "from": "node-entry",
              "to": "node-demo",
              "bidirectional": true,
              "enabled": true,
              "reviewed": true,
              "estimatedTravelSeconds": 90
            }
          ]
        }
      ]
    }
  }
}
```

上面地点和通行时间均为说明格式的虚构示例，不是 REDLAND 数据。最终 Schema 必须补齐字段定义、数值边界和关联语义，示例资产也要真实随测试包提供。

### 12.3 可实际使用的导入导出

网页提供 JSON 文件、文本粘贴、示例下载；地图通过单独文件选择与 assetKey 绑定，不要求把图片编码入 JSON。

- “JSON 活动资料”与“含图片的便携资料包”是不同导出方式，要在 UI 说明。前者不能假称包含地图原图。
- P0 至少完成 JSON＋地图文件的关联导入。ZIP 便携资料包可作为增强；若实现，限制解压总大小、条目数，拒绝路径穿越和压缩炸弹。
- 禁止根据 JSON URL 自动抓任意远程图片、Schema 或内网资源。外部链接可作为来源说明，不自动当作导入任务。
- 不把绝对服务器路径、私密签名地址、Cloudflare/Vercel token 写进标准活动包。
- 预览展示新增/变更/移除的活动、地点、地图与通道，以及受影响的计划。服务端重新校验后提交。
- 缺资产、哈希不一致、非法坐标、悬空 ID、地图版本不符、负/零路线权重、错误方向、跨活动引用都要给字段路径和可读错误。
- 同一个包重导入不能重复创建所有摊位；更新有权限和版本检查，失败不覆盖原活动。
- v1 原有大小限制保留；新格式另设有界限制并在真实运行时测 CPU/内存。不能为了支持大图把 JSON 限制无限放大。

最终必须交付：旧格式兼容样例、通用活动新格式样例、带小型虚构地图与可走通道的完整漫展示例、REDLAND 空框架/已核实数据包、明确失败样例，以及新 Schema。

REDLAND 资料只能来自用户提供或经核实有权使用的来源。原先 09:00–21:00 是待确认默认开放时间，不是官方结论；未提供真实地图、真实场次和可走通道时，不得编造后宣称已可现场导航。

## 13. 部署选择：默认无需自有服务器，按实际条件决定

### 13.1 技术决策原则

“完整项目”指业务、数据、权限、文档、恢复与发布闭环，不意味着一定要有一台自己维护的服务器。

默认沿用 dots 当前已经验证的托管架构；若仍按旧 Prompt，则是 Vite/React 前端＋Worker API＋D1。地图显示、手动标点、轻量路线计算和本机定位无需强制改为常驻服务器。

**首发必须有一种不购买/不维护自有服务器也能运行的完整在线方案，不得缩水为纯静态或单机版。**

在 README 和 `docs/DEPLOYMENT_DECISION.md` 记录实际选择、依据和限制：现有完成度、用户真实网络可达性、图片存储、数据库额度、数据可迁移性。不要用角色数量作为必须自建服务器的理由。

### 13.2 托管方案的媒体存储

地图上传需要真正持久的媒体存储。先复用已验证、满足预算和权限要求的现有方案。

尚未选型时，可优先评估当前 Vercel Hobby 的 Blob 免费额度及兼容的上传方式；正式使用前核对账号计划、条款、限额、私有资产支持和全部相关费用。

R2 等对象存储虽然有免费额度，可能需要开通计费订阅并有超额计费，不能称为无条件零费用；未经用户明确同意不得开通新的付费/可自动计费订阅。

- 不把完整地图传给每次列表请求，不随着个人资料重复下载。
- 媒体服务限额耗尽可能影响读取，不只是上传；提前缓存、监控和提供列表兜底。
- 前端可有预处理，但最终权限、文件类型、大小和资产归属由可信端校验；免费 Worker 不适合做的重图像处理不能无限放到其请求里。
- 不能把 Vercel 函数临时磁盘当作持久上传目录。
- 静态随构建地图可做应急只读展示，不得伪装成后台上传已经成功。
- 绝不为了“免费”向 GitHub 公共仓库写入用户数据、私密地图或业务密钥。

### 13.3 可自托管能力

保留独立部署的能力边界：业务服务不直接到处依赖平台 SDK，数据库与媒体操作集中在薄适配层，共享 DTO、校验、鉴权和算法。

若当前已有成熟服务器实现，保留它，并核实无需自有服务器的版本同样能跑核心业务。若目前只有 serverless 实现，**不要在 10 月 3 日前为了形式上“双版本”重写另一套完整业务**。

自托管适配作为 P1：可采用相同 TypeScript 业务＋Node HTTP 入口＋SQLite 持久卷或项目已稳定使用的数据库＋本地持久资产目录，提供 Docker Compose/等效说明及迁移测试。不能声称未实现的适配器已可用。

- 自托管软件可以不额外付费，但服务器、域名、带宽不是自动免费。
- 不强制改用 MySQL/PostgreSQL、Redis、消息队列和 Kubernetes。
- 两种部署用同一套协议/权限/分钟算法，不形成两个长期分叉仓库。
- 数据与资产可导出迁移；迁移时保留稳定资源 ID、版本和凭据验证一致性，改变域名需要安全恢复入口，不能假称浏览器本地数据自动跨域迁移。
- 每次部署只选择一个有效后端，不做双写、跨云自动切换或混合主库。

切换服务器的合理触发条件是实际托管限制、网络可用性或运行需求，不是“功能多看起来应该上服务器”。真正发现阻断再集中说明，不提前要求用户购买。

## 14. 安全、离线和地图版本的一致性

### 14.1 保留原安全底线

能力凭据高熵、权限按资源限定、服务端校验、撤销轮换、CAS、幂等、参数化 SQL、严格输入校验、日志脱敏继续生效。

地图、地点名称、来源、用户备注均安全渲染，不允许注入 HTML/脚本。接口返回 DTO 不包含不该共享的私人数据，不能依靠 CSS 隐藏。

新角色/上传接口单独测权限，不复用一个无范围万能 token。未经授权不接入同野主站 SSO。

### 14.2 离线准备

提供可见的“为现场准备离线数据”入口，让用户选择当前活动的地图、地点列表、通道和个人计划快照，并显示估计大小、版本、缓存成功/失败与最后更新时间。

- 第一次从未下载不能说可以完全离线使用。
- 公开活动缓存与私人快照分开。退出或删除本机记录有对应清理；不能把私人 API 放公共缓存。
- 离线可查看已下载资料、调整本地路线、保存草稿；新建小队、接受邀请、多人更新等网络操作不能假称成功。
- 底图和图数据按版本一起激活，避免旧底图配新路线。新版本下载失败保留可识别的旧快照并显示过期。
- 地图失败时保留收藏列表和时间安排，不能整页白屏。
- Service Worker 更新不强制刷新丢草稿；新 JSON/数据库版本与旧客户端有兼容策略。
- 同步冲突保留本地变更，不静默覆盖；不能把 `localStorage/IndexedDB` 说成加密保险箱或异地备份。

### 14.3 网络与额度

沿用可见且在线时有界刷新策略，隐藏页面停止，不为地图拖动、GPS 回调或每个收藏按钮建立轮询。合法写请求在会场同一 Wi-Fi 下不要互相误封。

按假设规模测量，而不是声称实际已有相应用户：先覆盖每队 50 人、五天活动、约 1000 个地点/场次级别的数据，地图数量和尺寸有明确边界。客户端拥挤标点和图算法有性能记录，Worker 批量校验有额度实测。

使用中国大陆实际网络验证前端、API 和图片地址；远程开发环境能打开不能算现场网络验证。缺真机或网络条件就如实列出待验。

## 16. 首发范围与执行顺序

### 16.1 P0：此次必须完整交付

1. 新品牌和活动优先入口；通用/漫展两类有实际差异。
2. 管理员能创建和编辑活动，不改代码完成公开资料发布。
3. 漫展地图实际上传持久化、显示、缩放、标点与地点关联。
4. 摊位/设施列表和搜索、收藏/去过状态、个人计划与场次互通。
5. 个人路线站点顺序、手动起点；有已确认路网时生成正确路径，没有时诚实降级。
6. 可实际操作的最小通道编辑器，能准备 REDLAND 本次需要的一段可信路线，而不是只有开发者可写 JSON。
7. 既有多人同步、三角色权限、分钟算法、确认状态、旧数据兼容和保护全部保留。
8. 新旧 JSON、地图文件绑定、Schema、示例和文档闭环。
9. 离线准备、错误状态、备份恢复、真实部署及核心流程验证。
10. 一个不需要自有服务器的完整在线部署方式。

### 16.2 P1：不得阻塞首发

GPS 地理配准和实时定位、多楼层自动路线、自由站点顺路优化、实时共享位置、复杂集合投票、全站账号/SSO、自托管新适配器、任意截图识别、3D 地图和自动人流分析。

已经实现且验证通过的 P1 可以保留，没实现的不能以可用按钮承诺。**顺路优化可以后做，但 P0 的路线清单、手动起点、人工路网与按路网走不能全被降级掉。**

### 16.3 实施顺序

A. 核对当前代码和待办，先保存基线测试与功能状态，列出新需求影响，不回退到旧 UI。

B. 先完成活动优先路由、类型、个人计划与小队关联，跑通不组队浏览和原有组队流程。

C. 完成管理员活动编辑、POI、收藏、场次关联和 JSON 升级，同时完成权限测试。

D. 完成地图真实上传、标点、列表联动和版本校对，再做通道编辑与固定顺序路线。

E. 接入路线与分钟日程的可行性提醒、离线准备、数据更新状态和错误降级。

F. 做迁移回归、文档演练、隔离环境多人测试、备份恢复，再发布首发版本。

G. 核心稳定后按条件做定位或自托管，不在功能未闭环时反复探索新框架和竞品。

各阶段先写关键失败测试再实现。每阶段有可运行交付和小步提交，不批量写完后才第一次启动。

## 17. 必须落地的验收矩阵

### 17.1 产品与角色

- 普通用户先选活动；邀请链接直接到相应活动/小队；切换活动不串收藏、地图和计划。
- 不组队也能收藏并维护个人计划；随后加入小队无需丢弃已有数据。
- 通用活动不强迫上传地图或填写展位/IP。
- 队长不能改公共活动，成员不能改别人或跨队读取；管理员的普通用户视图不带私密成员数据。
- 活动草稿、私有图、已下架资料不因公开 API 或缓存策略而被错误发布；已下载副本不能被承诺远程抹除。

### 17.2 收藏与分钟级计划

- 同活动同地点重复收藏幂等；同编号跨活动互不影响；改名不丢收藏；删除 POI 后正确显示失效。
- 收藏不自动变忙，加入路线不自动变预约，取消收藏不删除已有日程。
- `13:07–13:52` 经过选择、保存、刷新、导出回导与路线计算均不变。
- 原精确共同空闲样例全部通过；未提交不算全天可用；个人缓冲不被其他人全局设置覆盖。
- 资料时间版本变更要求复核，纯标题修订不让全员无意义重填。

### 17.3 地图与资产

- 非正方形地图 2000×1000 中 `(0.25,0.6)` 对应图像点 `(500,600)`；缩放/平移/屏幕旋转后点位仍正确，不把容器留白算进去。
- JPEG/PNG/WebP 正常上传后另一独立浏览器能读取；非法文件、超限、伪 MIME、无权限上传被拒绝。
- 上传成功但提交失败不损坏旧地图；替换图片不出现新图旧点默默错位。
- 375/390/430px 手机视口可看图、选点、收藏、关闭 Sheet，无整页横向溢出。
- 图像源、资源引用、访问权限与备份恢复一致，不只验证数据库导出存在。

### 17.4 路线与定位

- 测试图中 A 到 D 无直接边，只能沿 A→B→C→D，结果必须绕路，不能画 A→D 直线。
- 单向边不能反走，关闭边不参与，断开的地点提示无可用路段。
- 一部分路段缺计量依据时不显示假的完整米数/ETA；像素长度不能冒充米。
- 固定场次不被优化改变；无法到达下一场应提示，不自动删除该场次。
- 缺路网的活动仍能收藏、看图、排时间和维护站点顺序。
- 关闭边/更换底图后既有路线失效，重算使用同一套最新匹配版本。
- 缓冲与通行时间不重复叠加，未知时间不是 0。
- 若交付定位：权限拒绝、低精度、超时、无配准、地图外、关闭监听全部测试；抓包证明默认不上传位置，模拟定位不冒充真机实测。

### 17.5 持久化与上线

- 三个独立浏览器身份扮演管理员、队长、队员，从创建发布、上传地图到收藏排程、小队比对走通。
- 同版本并发修改仅一个成功，失败者草稿还在；重试不重复建队/成员/地点。
- 离线能看已下载地图和计划，未提交变化有明确提示；重连不覆盖新版本。
- 旧本地数据、备份和分享入口仍能安全读取，旧人名不变成真实在线成员身份。
- 按文档从空环境部署托管方案；API、图片地址和数据库都是真实的。
- 预发布数据库＋地图资产导出后，在隔离环境恢复并实际打开地图、收藏和个人安排。
- 生产切换前有回滚依据，生产只读验证版本、就绪与路由；不得对真实成员运行破坏性测试。
- 没有实机/大陆网络条件时写明待验，Playwright WebKit 不称为 iPhone 真机通过。

## 18. REDLAND 现场准备与发布停止条件

把“软件完成”和“REDLAND 资料准备完成”分成两个检查项。

用户需要提供或确认的真实资料可能包括：活动开放时间、可用地图及使用来源、展位/场次列表、地图上关键位置、入口与实际可走通道。集中列清，不要求为了全场完美建模而推迟软件核心。

首发至少准备：

- 2026-10-03 的实际使用日期与分钟安排。
- 一张能辨识的真实地图；没有来源不能用虚构图冒充。
- 用户实际会去的入口、几个摊位/场次位置。
- 至少一段核实过的通道，用来演练路线；缺失部分明确不可导航。
- 一个真实小队的预发布演练，再由用户建立正式小队，不自动迁入测试人员。
- 手机上提前完成离线准备和身份恢复入口保存。

若关键安全、保存、分钟计算或版本回归失败，不得发布为完成版；保留此前稳定功能并明确阻断。定位或顺路优化未完成不阻止首发，真实地图/通道未备齐则降低路线覆盖声明，不伪造数据。

## 19. 最终交付格式

最后按如下结构交付，不要只说“做完了”：

1. **本次改动**：活动优先结构、类型、收藏、地图、路线和原有同行如何联通。
2. **真实范围**：P0 各项结果，P1 已完成/未完成；什么是真地图、什么是示例。
3. **代码与部署**：分支/提交、实际已部署环境、对应版本；未部署写具体阻断。
4. **测试证据**：运行命令、通过/失败、浏览器/设备、网络环境；不能混用模拟与真机。
5. **数据与兼容**：JSON 格式版本、旧格式迁移、地图引用、备份恢复和回滚。
6. **文档入口**：新手、管理员、地图标注、JSON、部署、现场准备的准确位置。
7. **用户最少必要动作**：只列仍需授权、资料确认和真机操作，不甩回一般性工程选择。
8. **部署判断**：当前为什么采用托管或服务器方案，无自有服务器方案如何运行，自托管是否真正实现。
9. **已知边界**：免费限额、真实网络、路网覆盖、估计时间、地图配准和离线信息时效。

开始执行：读现状与原计划，保护已完成工作，按本文修订任务，优先把“选活动→收藏→安排→地图路线→小队同行”接成真实闭环，再完善验收和发布。不要只增加页面数量，也不要以服务器选型为理由停在讨论阶段。
